# WebRTC P2P prototype

Изолированный технический прототип поиска двух браузеров через Cloudflare Durable Object и передачи сообщений напрямую через WebRTC DataChannel. Игровой логики нет.

## Архитектура

- Cloudflare Worker отдаёт статические файлы и проксирует `/ws` в один Durable Object.
- SQLite-backed Durable Object хранит FIFO-очередь, временные пары и состояние подтверждения подключения. В сигнализации передаются только SDP и ICE.
- Пара считается подтверждённой сервером только после `ready` от обоих клиентов.
- Браузеры устанавливают `RTCPeerConnection` с публичным STUN-сервером Google. После открытия DataChannel текстовые сообщения передаются только между браузерами; Worker их не получает.
- TURN не настроен. При ограничениях NAT/firewall прямой ICE-маршрут может не установиться — для таких сетей потребуется TURN-сервер.

## Требования

- Node.js не ниже 22 (Wrangler 4).
- npm.
- Для публикации: Cloudflare account и Wrangler CLI authentication.

Проверенная при подготовке актуальная версия Wrangler: `4.156.0`; она закреплена в `package.json`. Wrangler хранит состояние авторизации вне репозитория. Не добавляйте токены в файлы проекта.

Конфигурация Wrangler нацелена на Worker `fancy-math-9ab8` и включает endpoint `workers.dev`. Ожидаемый адрес после публикации в нужном аккаунте: `https://fancy-math-9ab8.egorpcp.workers.dev`.

## Локальный запуск

Из каталога `webrtc-prototype` выполните:

```powershell
npm install
npm run dev
```

Откройте показанный Wrangler адрес, обычно `http://localhost:8787`, в двух независимых браузерных вкладках. Нажмите «Подключиться и искать игрока» в обеих. После открытия DataChannel отправьте сообщение в каждом направлении.

Локальный Wrangler эмулирует Worker и Durable Object с локальной SQLite. Две вкладки проверяют сигнализацию и обмен трафиком в данной среде, но не подтверждают проходимость NAT между разными сетями.

## Публикация Cloudflare

Публикацию выполнять только после отдельного разрешения владельца проекта. Команда развёртывания намеренно не запускалась.

После разрешения:

1. Выполните `npm install`.
2. Войдите в Cloudflare командой `npx wrangler login`. Не копируйте выданные credentials в файлы проекта.
3. Убедитесь, что выбран именно Cloudflare аккаунт с поддоменом `egorpcp` и Worker `fancy-math-9ab8`.
4. Выполните `npm run deploy`.
5. Откройте адрес вида `https://<worker-name>.<account-subdomain>.workers.dev` в двух браузерах и проверьте сообщения в обе стороны.

`wrangler.jsonc` использует актуальный migration формат `new_sqlite_classes` для SQLite Durable Object. Cloudflare создаёт ресурс Durable Object при первом deploy; для этого прототипа не требуется вручную добавлять ID namespace.

Понадобится отдельное разрешение перед публикацией. Первое развёртывание регистрирует SQLite Durable Object migration в аккаунте.

## Очистка и обработка сбоев

- Client ID и ID пары создаются сервером отдельно для каждого подключения.
- Один Durable Object сериализует подбор; игрок удаляется из очереди до создания пары.
- Повторный запрос поиска от одного подключения идемпотентен; клиенту нельзя одновременно состоять в двух парах.
- Закрытие WebSocket удаляет игрока из очереди и сообщает его сопернику об отключении.
- Heartbeat обновляет время активности; устаревшие записи и незавершённые пары чистятся при следующем сообщении/подключении.
- Подтверждение обоих клиентов и ограничение ожидания не позволяют считать пару найденной только по одному ответу.
- SDP/ICE и сообщения сигнализации ограничены размером; DataChannel сообщения идут отдельно от Worker.

## Ограничения прототипа

- Это прототип сигнализации, не production matchmaking: очередь одна на весь Worker, нет фильтров режима, авторизации, антиспама и метрик.
- SQLite и состояние DO локальны для Wrangler при разработке и не являются копией production Cloudflare данных.
- Соединение между двумя вкладками одной машины не заменяет тест на двух устройствах в разных сетях.
- В первой версии нет TURN fallback, сохранения сессии после рестарта Worker или автоматического переподключения.
- Используется публичный STUN Google; доступность и политика этого сервиса находятся вне контроля приложения.

## Итоговая проверка

1. Статус каждого клиента переходит от подключения к поиску, подтверждению пары и WebRTC setup.
2. ID обоих игроков должны отображаться взаимно.
3. В журнале должен появиться `DataChannel открыт`.
4. Отправьте уникальную строку из каждой вкладки и убедитесь, что она появилась во второй вкладке.
5. Проверьте отмену поиска, закрытие одной вкладки и повторный поиск.

## Подключение сетевого клиента

Сетевой транспорт вынесен в `public/online-client.js`. Страница прототипа использует `public/client.js` только как DOM-адаптер; модуль транспорта не обращается к элементам страницы.

Перед импортом клиента можно задать конфигурацию через `globalThis.TICTACTOE_ONLINE_CONFIG`:

```html
<script>
    globalThis.TICTACTOE_ONLINE_CONFIG = {
        signalingUrl: "wss://your-worker.example/ws",
        rtcConfiguration: {
            iceServers: [{ urls: "stun:stun.l.google.com:19302" }]
        }
    };
</script>
<script type="module" src="./client.js"></script>
```

Если `signalingUrl` не задан, конфигурация использует `/ws` на текущем origin (с `wss:` на HTTPS). Адрес Worker не зашит в сетевом модуле.

Основной API `OnlineClient`:

- `new OnlineClient(config)` — создать экземпляр транспорта;
- `connect()` — открыть сигнальный WebSocket;
- `search(options)` — подключиться и встать в очередь поиска;
- `cancel()` — отменить поиск или настройку найденной пары;
- `send(stringOrObject)` — отправить текст или JSON через открытый DataChannel;
- `disconnect()` / `dispose()` — закрыть соединения и освободить ресурсы;
- свойства `state`, `clientId`, `peerId`, `match`, `isDataChannelOpen` — текущее состояние;
- `on(eventName, listener)` — подписаться на событие; возвращает функцию отписки. Обработчик получает объект `detail`.

Ключевые события: `statechange`, `welcome`, `searching`, `matchfound`, `matchstart`, `datachannelopen`, `message`, `cancelled`, `peerleft`, `connectionlost`, `error`. Клиент предоставляет только поиск/сигнализацию и универсальную передачу сообщений. Игровой протокол, синхронизация поля и статистика в этом этапе не добавлены.
