# Первичный аудит статистики и источники VK Mini Apps

Дата проверки: 2026-11-06. Этот документ фиксирует найденные факты и открытые вопросы для PH-001/PH-006/PH-011. Он не утверждает, что статистика или ссылка на сообщество уже интегрированы. Статусы проекта — в [PROGRESS.md](../PROGRESS.md), решения — в [DECISIONS.md](../DECISIONS.md).

## Аудит исходного кода

### A. Локальная статистика и состояние

| Данные/показатель | Фактическая реализация | Хранение/отображение |
|---|---|---|
| История завершённых матчей | id, completedAt, result, winner, mode, boardSize, difficulty, durationMs; только валидные поля/значения принимаются, дубликат match ID отклоняется. | localStorage key tictactoe.player-stats.v1, JSON schemaVersion 1. |
| Количество матчей | Считается в выбранной категории сложности и размера поля; текущий агрегатор включает computer и online режимы. | UI показывает количество сыгранных партий. |
| Победы/поражения/ничьи | Считаются в getCategoryStats и getOverallStats, но отдельные значения не отображаются текущим UI. | Только расчётный API модуля. |
| Фильтры категории | Три сложности (easy, medium, hard) × три размера (3, 4, 5). | Выбранные фильтры живут в памяти страницы; сохранение настроек не найдено. |
| Лучшее время | Минимальная длительность победы X в режиме computer; онлайн-победы в best time не входят. | UI показывает для выбранной категории. |
| Таймер и прошлый результат | Длительность текущей завершённой партии записывается в match record; таймеры и отображение предыдущего результата страницы — состояние в памяти. | Match duration сохраняется в local history; «предыдущий результат» сбрасывается после перезагрузки. |
| Локальный профиль | displayId формата ID_DDMMhhmmss и случайный identityKey; профиль schema 1. getPlayerIdentityKey в основном приложении не вызывается. | localStorage key tictactoe.player-profile.v1; не является VK identity. |
| Привязка матча к пользователю | Ни playerId, ни identityKey не записываются в match record. | Отдельные профили пользователей в одном browser origin не изолированы. |
| Ошибки хранилища | При недоступном localStorage используется module-local Map без долговременной персистентности. Некорректные данные модуль пытается сохранить под backup-ключом и восстановить store. | Никакой облачной копии нет. Необходимо сохранять исходные ключи при будущей миграции. |
| Рейтинг | index.html содержит placeholder места и десять строк leaderboard; script.js создаёт пустые строки. | API загрузки/записи рейтинга и серверный источник данных не найдены. |

### B. Пользовательская статистика

Сейчас display ID — локально сгенерированное значение, а не идентификатор Mini Apps. Запись результата связана с событием завершения партии, но не с профилем. Между двумя людьми, использующими один origin/localStorage, строгой изоляции нет. Идентификация пользователя и безопасное объединение старой истории с аккаунтом отсутствуют.

### C. Облачное хранение и передача данных

- В основной игре не найдено вызовов статистического API, fetch к backend, IndexedDB или VK Bridge Storage.
- В online-игре script.js передаёт игровой peer-traffic (ходы и итог матча) по WebRTC DataChannel. Это не upload статистики в серверное хранилище.
- Cloudflare Worker/Durable Object из webrtc-prototype обслуживает matchmaking/signaling и состояние очереди/пары. Код не реализует пользовательскую историю, облачную синхронизацию или leaderboard.
- Яндекс SDK не используется: в исходниках приложения и сетевого прототипа не обнаружены YaGames, ysdk или вызовы Yandex Games API. Также не найден VK Bridge integration.

### D. Универсальная и платформенная часть

Универсально и уже реализовано: схема match record, локальная запись/валидация, подсчёт сводки и UI-фильтрация. Платформенно и пока не реализовано: VK user context, авторизация/проверка identity, user isolation, platform storage, межустройственная синхронизация, глобальный рейтинг и его anti-cheat. Их следует вводить отдельными адаптерами, оставляя local provider доступным для guest/offline сценария.

## Первичное исследование официальных материалов

Проверены VKCOM-maintained исходники VK Bridge и Mini Apps типов. Прямые страницы соответствующей документации на dev.vk.com через доступный web lookup не открылись; поэтому выводы ниже ограничены обнаруженными первичными репозиториями. Перед реализацией нужно повторно сверить каждый пункт с актуальной документацией портала VK Mini Apps и целевыми клиентами.

1. [VKCOM/vk-bridge](https://github.com/VKCOM/vk-bridge) описывает библиотеку как интеграцию VK Mini Apps с официальными клиентами VK для iOS, Android и Web.
2. [Исходник VK Bridge core](https://github.com/VKCOM/vk-bridge/blob/master/packages/core/src/bridge.ts) содержит методы/события профиля, community operations, storage (VKWebAppStorageGet, VKWebAppStorageSet) и открытие другого приложения (VKWebAppOpenApp). Проверенный исходник не даёт достаточного ответа о рекомендованном вызове для открытия произвольной страницы сообщества. Нельзя выводить из наличия community methods, что это методы навигации на публичную страницу.
3. [Документация VKCOM vk-mini-apps-api](https://github.com/VKCOM/vk-mini-apps-api/blob/master/docs/classes/vkminiappapi.md) документирует Storage методы как обёртки VKWebAppStorageGet/GetKeys/Set, с указанными там платформами iOS/Android/Web. Репозиторий архивный; это доказательство существования метода в SDK-материалах, но не подтверждение текущих квот, retention, cross-device гарантий или пригодности для больших history/leaderboard.
4. [Типы launch params в VKCOM/vk-mini-apps-router](https://github.com/VKCOM/vk-mini-apps-router/blob/master/typings/vk-bridge/index.d.ts) содержат поля vk_user_id и sign. Одного наличия типов недостаточно для утверждения о безопасной серверной аутентификации: нужно проверить текущую официальную процедуру формирования/проверки подписи, expiry/replay и требования backend.

### Предварительные выводы — не утверждённая архитектура

- Для community CTA рассмотреть обычную user-initiated HTTPS-ссылку и проверенный VK Bridge путь только после подтверждения в актуальной документации. Получить реальный URL после создания страницы. Проверить mobile VK client и desktop Mini Apps отдельно. Не использовать window.open/Bridge method как принятое решение без источника.
- Для сохранения personal progress изучить официальный platform storage отдельно от leaderboard. Требуются гарантии квоты, retention, изоляции по приложению/пользователю, поведения на разных клиентах и доступности в browser fallback.
- Для leaderboard нужен доверенный способ проверки результата. Хранение произвольных ключ-значений само по себе не подтверждает server-side integrity. Собственный backend остаётся вариантом к оценке, а не решением.
- Старую историю переносить только при понятной привязке к пользователю и по отдельно согласованной политике. Импорт должен быть opt-in или иным образом одобренным, идемпотентным, сохранять local source/backup и не смешивать данные разных аккаунтов.

## Что ещё необходимо проверить

- Точный актуальный способ открыть сообщество из VK Mini Apps и UX/API для desktop/mobile.
- Разрешён ли внешний линк на сообщество в приложении и какие требования действуют для модерации, target и перехода обратно.
- Требуется ли отдельная версия/feature detection для Mini Apps, чтобы убрать только CTA Дзена внутри этой версии, сохранив канал внешне.
- Текущая официальная семантика VK Bridge Storage: пределы, lifetime, область аккаунта, кросс-устройственное чтение, reset и режим вне VK.
- Каким способом доверенно проверить пользователя и результат матча на стороне сервера.
- Требуется ли собственный сервер для синхронизации/общего рейтинга и какие правила ранжирования нужны.
- Как импортировать матчи без player ID, если на устройстве появятся несколько VK-пользователей.

## Онлайн-концепция и test setup (2026-11-06)

Продуктовый сценарий от владельца определён: быстрый случайный матч по одной кнопке с автоматическим поиском среди пользователей в приложении и автостартом. Приглашения, коды комнат, ручное создание комнат, ссылки на матч и обязательная дружба в обязательные требования не входят. Это продуктовая договорённость, она не утверждает технический протокол.

Проверка текущего [Worker](../webrtc-prototype/src/worker.js) и [описания прототипа](../webrtc-prototype/README.md) подтверждает FIFO очередь и временное создание пары через Durable Object; дальше Worker передаёт сигнализацию WebRTC, но игровой DataChannel трафик и результат матча сервер не контролирует. Нет авторитетного игрового состояния, валидации ходов, VK user mapping и production reconnect. Это означает: часть matchmaker-механики экспериментально реализована, но завершённого multiplayer backend нет.

Варианты для дальнейшей оценки: (а) WebSocket к серверно-авторитетному матчу; (б) Worker + Durable Objects, расширенные управлением состоянием матча; (в) WebSocket matchmaking с WebRTC data path; (г) чистый P2P с отдельной проверкой результатов. WebSocket модель концептуально облегчает проверку очередности и результата на сервере; WebRTC P2P может передавать сообщения напрямую, но сам по себе не делает клиент достоверным и требует оценки NAT/TURN. Это качественные архитектурные гипотезы, не измерения latency/стоимости и не утверждённый выбор. Проверить лимиты/цену у фактически выбранного хостинга и согласовать архитектуру до реализации.

Для test setup найден официальный пример репозитория [VKCOM/vk-mini-apps-examples](https://github.com/VKCOM/vk-mini-apps-examples), который описывает в своих инструкциях раздел приложения «Тестирование» и VK Tunnel для направления VK-запуска на локальный сервер. Это свидетельствует о доступности такого workflow в примерах, но не фиксирует текущие разрешения проекта, размер тестовой группы, конкретные account limits или доступность каждого SDK/API/рекламы в тестовом режиме. Эти детали надо проверять в актуальном кабинете приложения и текущей документации; тестовая группа не является доказательством production-поддержки функций.

Официальный архивный пример [VKCOM/vk-apps-launch-params](https://github.com/VKCOM/vk-apps-launch-params) показывает передачу launch parameters включая `vk_user_id` и `sign`, а также пример серверной проверки подписи. Архивность примера и отсутствие проверки актуальной процедуры на живом официальном портале означают, что это лишь исследовательская зацепка. Перед внедрением повторно проверить текущие требования Mini Apps: состав подписываемых параметров, срок действия/повторное использование, secure key handling, формат передачи серверу и допустимую интеграцию.

### Открытые вопросы multiplayer

- Подтверждает ли актуальная официальная документация Mini Apps рекомендованную авторизацию/проверку launch data именно для backend данного проекта?
- Есть ли платформа-managed realtime/matchmaking API для Mini Apps, и какие обязанности остаются разработчику? Пока готовый игровой matchmaking сервер не подтверждён.
- Какие hosting/DO ограничения и тарифы подходят для очереди и авторитетного состояния пошагового матча, включая reconnect и хранение матча?
- Какой grace period и итог назначать при уходе игрока; можно ли восстановить матч на другом клиенте; как дедуплицировать команды и результаты?
- Какие конкретные возможности доступны тестовым пользователям и какие ограничения накладываются на рекламу/сеть/профили?

Реестр решений и сопоставление требований см. в [DECISIONS.md](../DECISIONS.md), [REQUIREMENTS.md](../REQUIREMENTS.md), [TASKS.md](../TASKS.md), [TESTING.md](../TESTING.md) и [ARCHITECTURE.md](../ARCHITECTURE.md). Подробные сценарии тестирования описаны там; фактических прогонов в этой работе нет.
