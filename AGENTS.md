# Регламент работы ИИ-агентов (TicTacToeA_VK)

## 1. Назначение и границы проекта
- Проект: браузерная игра «Крестики-нолики», подготавливаемая к запуску как **VK Mini Apps**. Базовая игра уже реализована.
- Целевая платформа — **исключительно VK Mini Apps**. VK Play и Яндекс Игры категорически не входят в проект.
- Концепция мультиплеера: быстрый случайный онлайн-матч по одной кнопке. Ручные комнаты, коды и инвайты друзей исключены.

## 2. Стратегия разработки (DEC-010)
- **Принцип:** Мы **НЕ** тестируем в реальной среде VK Mini Apps после каждого отдельного модуля.
- Сначала максимально полно разрабатывается готовый продукт в локальной среде (бэкенд, авторитетные матчи, клиентский онлайн, статистика, адаптеры), и только затем проводится перенос и комплексные испытания в реальной среде VK Mini Apps.
- **Два режима работы (единая кодовая база):**
  - `Development Mode`: локальный запуск, тестовая авторизация (искусственные аккаунты), мок-адаптер VK Bridge, возможность запуска двух окон/клиентов для проверки матчей и статистики;
  - `VK Mini Apps Mode`: реальная авторизация параметров запуска VK, вызовы `@vkontakte/vk-bridge`, боевой бэкенд.
- Тестовые механизмы должны быть недоступны в релизной сборке.

## 3. Порядок изучения проекта
1. Начинать работу строго с **`TASKS_AI.md`** (главная карточка передачи контекста, текущий статус, задачи, отложенные решения и журнал изменений).
2. Ознакомиться с этим файлом (`AGENTS.md`), затем с [README.md](./README.md) и [ARCHITECTURE.md](./ARCHITECTURE.md).
3. Проверить реальный исходный код и конфигурацию. Документация не заменяет проверку кода.
4. Отличать подтверждённые функции от запланированных. Не выдавать планы за факт.

### 3.1. Минимально достаточный объём работы — обязательные правила
Агент самостоятельно выбирает минимально достаточный объём анализа, изменений и проверок. Экономия ресурсов не отменяет проверок, критичных для безопасности, целостности данных и основного функционала.

1. Не проводить полный аудит проекта перед каждой задачей. Использовать результаты предыдущей работы и изучать только необходимые файлы.
2. Не перечитывать всю документацию, если достаточно конкретных актуальных разделов.
3. Не составлять многостраничные планы для небольших изменений.
4. Не создавать тесты на очевидные вещи: наличие кнопки, текста или элемента интерфейса.
5. Не запускать полный набор тестов после каждого изменения; выбирать минимальный достаточный набор.
6. Не проверять одну функцию несколькими избыточными способами.
7. Не переписывать документацию целиком после каждого этапа.
8. Не заниматься рефакторингом, если он не требуется для текущей задачи.
9. Не исправлять проблемы, не относящиеся к текущей задаче.
10. Не тратить запросы на длинные объяснения очевидных действий.
11. Не создавать дополнительные планы, отчёты и вспомогательные документы без реальной необходимости.
12. Если критерий задачи подтверждён одной достаточной проверкой, не продолжать проверки ради их количества.
13. Если проверка невозможна из-за отсутствия окружения или инструмента, указать конкретное ограничение и не тратить ресурсы на бесконечную настройку среды.
14. О посторонней проблеме кратко сообщить, но не устранять её без необходимости.

## 4. Правила изменения кода и зависимостей
- Выполнять только задачу, поставленную пользователем.
- Сохранять существующую базовую логику игры и ресурсы (`game-logic.js`, `player-stats.js`).
- Изменения должны быть точечными и согласованными с архитектурой. Не изменять код игры при чисто документационных задачах.
- Не устанавливать, не обновлять и не удалять зависимости без прямого разрешения пользователя.
- Не создавать секреты в репозитории и не выводить их в отчёты.

## 5. Ограничения и согласования
- **Запрещено без согласования:** менять архитектуру, удалять функции, выбирать непроверенный бэкенд/хранилище.
- **Запрещено:** удалять или перемещать файлы проекта (кроме согласованной очистки документации).
- Любые архитектурные решения фиксируются в `TASKS_AI.md` со статусом `Proposed` до явного одобрения владельцем.
- **Принцип UI-002:** нижнее текстовое поле `#game-status` является основным и единым местом вывода всех игровых и сетевых сообщений. Запрещено создавать новые панели, модальные окна и дублирующие уведомления без согласования.
- **Принцип UI-001:** не изменять оформление и компоновку интерфейса до Этапа 5 (визуальная доработка); сохранять существующие Dev-механизмы.

## 6. Правила Git
- Не выполнять `git add`, `git commit`, `git push`, деплой или публикацию без прямого разрешения пользователя.
- Не переписывать историю Git.
- Перед любыми операциями с Git проверять `git status` и список remotes.

## 7. Актуализация документации и передача контекста
- Главный документ передачи контекста между сессиями и разными ИИ (ChatGPT, Gemini, Qwen, Claude и др.) — **`TASKS_AI.md`**.
- Перед началом работы каждый агент обязан изучить актуальный `TASKS_AI.md`.
- После каждого значимого этапа, аудита, исследования или изменения кода агент обязан:
  1. Проверить фактический результат и статус соответствующей задачи.
  2. Актуализировать `TASKS_AI.md`: зафиксировать проверенный итог, статус, дату, контрольный коммит, последнюю рабочую точку, конкретный следующий шаг и добавить запись в журнал изменений (раздел 12).
  3. Существенные изменения проекта кратко отразить в `CHANGELOG.md`.
- Использовать единые статусы: `Proposed`, `Planned`, `In Progress`, `Blocked`, `Review`, `Done`, `Deferred`, `Rejected`. Статус `Done` ставится только при наличии проверяемого критерия приёмки.

## 8. Формат отчёта
Кратко перечислить изменения и причины, указать выполненные проверки и результаты, отметить открытые вопросы и следующий шаг. Ссылаться на файлы проекта через markdown-ссылки. Явно указывать, если работа не включала тесты или коммиты.
